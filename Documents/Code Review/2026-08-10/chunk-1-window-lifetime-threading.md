# Chunk 1 — Window lifetime, state & threading

Range `c07260c..b215581`. Ledger: `progress.md`.

**10 findings — 1 BUG · 4 RISK · 5 CLEANUP. All `open`.**

## What was verified as correct

Recorded because each was specifically suspected and cleared by tracing, not by assumption:

- **`App.ForgetMiniGraph` is reached on all five destruction paths** (tray close, close glyph, Alt+F4, app exit, `_state.IsVisible = false`). `OnWindowClosed:235-240` orders `Teardown()` → `ForgetMiniGraph()` → `_state.IsVisible = false`; because `Teardown` has already unsubscribed `_state.Changed`, and `ForgetMiniGraph` has already cleared `_miniGraphVisible`, the App handler sees no change and no-ops. `CloseWidget` sets `_teardownStarted` before `Close()`, and `App.CloseMiniGraph:359-360` nulls the field synchronously. **No path leaves App holding a destroyed window.**
- **The `_appliedOrientation` split is correct at the point that writes settings.** `SaveCurrentPlacement:284-301` reads `_appliedOrientation`, so a debounced write landing after an orientation flip goes into the slot matching the geometry the window actually has. `OnStateChangedOnUiThread:717-744` flushes *before* mutating it, with the ordering documented in-comment. The `3144f8d` fix is right.
- **Restore/save is not a feedback loop.** In the constructor `RestorePlacement()` (line 127) runs *before* `AppWindow.Changed += OnAppWindowChanged` (line 131), so the initial placement never triggers a write-back. On the orientation-switch path the MoveAndResize → `ClampStripSize` → Resize chain converges in one extra hop and the resulting debounced save is idempotent with what `RestorePlacement` computed.
- **`WINEVENT_SKIPOWNPROCESS` is correct.** It suppresses foreground events generated by *our own* process; the taskbar is explorer.exe, so `Shell_TrayWnd` events still arrive. The flag buys exactly what its comment claims.
- **No race between the WinEvent callback and `Dispose()`.** `SetWinEventHook` is called with `WINEVENT_OUTOFCONTEXT` from the MiniGraphWindow constructor — the UI thread — so callbacks are delivered by that thread's message pump, and `Teardown()` also runs there. The non-volatile `_disposed` read at `TaskbarTopmostGuard.cs:135` is therefore safe, and `UnhookWinEvent` is called from the installing thread as required.
- **`MiniGraphState.Apply` is reentrancy-safe.** `changed` is evaluated by the caller before entry and `Changed` fires *after* `assign()` + `Save()`, so every handler reads fresh values. `SettingsViewModel.SyncMiniGraphFromState` deliberately bypasses the property setters, so there is no state → VM → state loop.
- **`MiniGraphViewModel.Attach`/`Detach` is guarded by `_attached`** and is symmetric across `ShowWidget` / `HideWidget` / `Teardown`, so no double-subscribe on the shared singleton feed.

## C1-1 `[RISK]` — `Bindings.StopTracking()` is never called, leaving a strong handler on a singleton

`NetworkMonitor/MiniGraphWindow.xaml.cs:265` · `MiniGraphWindow.xaml:55,64,107`

`Teardown()` carefully removes the hand-written `ViewModel.PropertyChanged -= OnViewModelPropertyChanged`, but never calls `Bindings.StopTracking()` — so the three `x:Bind` OneWay bindings (`ViewModel.InternetPoints`, `LocalPoints`, `UnknownDevicesText`) stay wired.

Verified in the **generated** code rather than assumed: in `obj/x64/Release/.../MiniGraphWindow.g.cs:392` the only lifecycle hook is `element1.Activated += bindings.Activated;`. For a **`Window`**-rooted `x:Bind` the compiler emits no `Unloaded`/`StopTracking` wiring at all (unlike a `Page`). `MiniGraphWindow_obj1_BindingsTracking.UpdateChildListeners_ViewModel` (lines 267-282) does a plain **strong** `PropertyChanged +=` on the ViewModel, and `MiniGraphViewModel` is registered `AddSingleton` (`App.xaml.cs:171`), so it outlives every window instance.

**Why it matters.** After Alt+F4 the tracking object stays subscribed to the singleton. Reopen the widget → the new window's `Attach()` → `Refresh()` raises `PropertyChanged` → the *old, destroyed* window's tracking object runs `XamlBindingSetters.Set_TextBlock_Text` against a disconnected XAML element, and the chart property setters call `SectionChart.MarkLiveUpdate()` on a torn-down control. The old object is only weakly reachable, so this is a timing window until GC rather than a permanent leak — but the window exists, and the failure mode is a disconnected-COM throw on a path with no handler.

**Fix.** Add `Bindings.StopTracking();` to `Teardown()`. `Bindings` is a private field on the same partial class (`MiniGraphWindow.g.i.cs:84`) and `IMiniGraphWindow_Bindings` exposes `StopTracking()` (line 71), so it compiles as-is.

**Status:** `open`

## C1-2 `[RISK]` — dispatcher callbacks queued before teardown can run after the window is destroyed

`NetworkMonitor/MiniGraphWindow.xaml.cs:712-715, 675-693, 717, 695, 701`

`OnStateChanged` and `OnViewModelPropertyChanged` both `DispatcherQueue.TryEnqueue(...)`. `Teardown()` unsubscribes the sources but does nothing about work **already sitting in the queue**, and none of the four targets check `_teardownStarted`:

- `OnStateChangedOnUiThread:717` → `ApplyLayout()` (touches `SectionsPanel`, `InternetSection`, …) and `RestorePlacement()` / `ClampMinimumSize()` → **`AppWindow.MoveAndResize` / `AppWindow.Resize` on a destroyed AppWindow**.
- `ApplySpeedTestText:695` / `ApplyUnknownDevicesBrush:701` → touch `SpeedTestLabel`, `UnknownDevicesLine`.

`Teardown` itself wraps its own `AppWindow` access in try/catch precisely because "Alt+F4 reaches here after the window is destroyed" (line 255). The same hazard applies to these four, unguarded.

The reachable sequence is a two-hop enqueue: `MiniGraphViewModel.OnFeedUpdated` posts `Refresh` (turn 1); `Refresh` raises `PropertyChanged`, which posts `ApplySpeedTestText` (turn 2). An Alt+F4 processed between those turns lands the second callback after `Closed`. Narrow, but real — and an exception here reaches `App.OnUnhandledException` → a fatal MessageBox, on what the user experienced as simply closing the widget.

**Fix.** Wrap `OnStateChangedOnUiThread`, `ApplySpeedTestText`, `ApplyUnknownDevicesBrush` and (for symmetry) `OnSavePlacementTimerTick` in `if (!_teardownStarted) { … }`.

**Status:** `open`

## C1-3 `[BUG]` — concurrent `Settings.Save()` can truncate `settings.json`, and a truncated file stops the app starting

`NetworkMonitor.Services/Data/AtomicFile.cs:16-19` · `NetworkMonitor.Services/Data/Settings.cs:284-291` · `NetworkMonitor/App.xaml.cs:88-91`

**Independently verified by the coordinator, not only by the auditor.**

`AtomicFile.WriteAllText` writes to `path + ".tmp"` — one fixed name, no lock — then `File.Move(tmp, path, true)`.

Writers of `Settings.Save()`:

| Caller | Thread |
|---|---|
| `ScanWorker.cs:238` (`RefreshSubnetBase`) | scan background loop |
| `MiniGraphState.cs:116` (`SavePlacement`) | UI |
| `MiniGraphState.cs:127` (`SaveStripPlacement`) | UI |
| `MiniGraphState.cs:147` (`Apply`) | UI |
| `MainWindow.xaml.cs:243`, `SettingsViewModel.cs:484`, `InternetViewModel.cs:106`, `LocalViewModel.cs:137,155`, `AllDevicesViewModel.cs:107` | UI |

The race is **pre-existing** — `ScanWorker` has always written from a background thread — but this change set widens it materially. Before, UI-thread saves were occasional (window placement, a Settings edit). Now the placement debounce fires on **every drag and every resize**, plus every opacity step, section toggle, orientation flip and border toggle, so the UI thread writes more or less continuously while the widget is being manipulated.

Two concurrent writers either lose one save (the second `File.WriteAllText` fails on the shared temp file — swallowed and logged at line 23) or, worse, thread A's `File.Move` publishes the file while thread B has it open truncated, leaving a **truncated `settings.json`**.

That is not recoverable at next launch. `App.xaml.cs:88-91` deserialises inside `ConfigureServices`, and `?? new Settings()` only covers a literal `null` document — malformed JSON throws `JsonException`, which propagates out of `Host.Build()` in the App constructor. **The user gets an app that will not start, and the only fix is to find and delete `settings.json` by hand.**

**Fix.** Two small, contained changes: give the temp file a unique name (`path + "." + Guid.NewGuid().ToString("N") + ".tmp"`), and serialise `Settings.Save()` behind a static lock. Optionally also wrap the deserialise at `App.xaml.cs:90` so a corrupt file falls back to defaults rather than blocking startup.

**Status:** `fixed` — 2026-08-11, fix-phase batch 1. Unique GUID temp name plus orphan cleanup in `AtomicFile.WriteAllText`; `Settings.Save()` serialised behind a static lock; the startup read in `App.xaml.cs` wrapped so a corrupt file falls through to the `appsettings.json` seed path, with the exception logged after `AppLog.Initialize` rather than at the catch site (where it would have been dropped). See `progress.md` → *Fix phase — batch 1*.

## C1-4 `[RISK]` — `App.ApplyMiniGraphVisibility` is the one `Changed` handler that doesn't marshal, and it constructs a `Window`

`NetworkMonitor/App.xaml.cs:284, 304, 322`

Line 284 subscribes `(stateSender, stateArgs) => ApplyMiniGraphVisibility()` with no dispatcher hop, and the body at line 322 does `new MiniGraphWindow(...)` plus `ShowWidget()` / `HideWidget()` — all strictly UI-thread-only.

Today this is safe: every `MiniGraphState` setter call site was checked and all are UI-thread (`TrayIconService.SubclassProc` runs on the main window's owning thread; the widget menu, `TrafficHostPage.MiniGraphToggleClick` and `SettingsViewModel` are all UI). But `MiniGraphWindow`, `TrafficHostPage` and `SettingsPage` **all** marshal defensively, so the class's own convention says "assume `Changed` may be raised from anywhere" — and the single handler that would crash hardest is the exception. Any future background writer (a hosted service auto-hiding the widget, a hotkey listener) breaks it silently.

Same method, separate point: `GetRequiredService<MiniGraphState>()` at line 304 sits **outside** the try/catch, so an `ObjectDisposedException` after `AppHost.Dispose()` would escape. Not currently reachable (`CloseMiniGraph` runs before `StopHost` in `ShutdownGracefully:303-304`), but the guard is free.

**Fix.** Hop through the main window's `DispatcherQueue` in the handler — or, at minimum, document the UI-thread requirement on `MiniGraphState.Changed`. Move line 304 inside the try.

**Status:** `open`

## C1-5 `[CLEANUP]` — `ClampMinimumSize` and `SectionsPanelSizeChanged` read `_state.IsHorizontal` while `_appliedOrientation` can be stale

`NetworkMonitor/MiniGraphWindow.xaml.cs:346, 372, 777-789`

`OnStateChangedOnUiThread:736-742` deliberately leaves `_appliedOrientation` stale when `!_state.IsVisible` — that is what tells `ShowWidget` a relayout is owed, and it is correct. But during that window:

- `ClampMinimumSize:777-789` (reachable from `OnAppWindowChanged:760` if something external moves or resizes the hidden window — a display disconnect, a DPI change) would run `ClampStripSize()` against a vertically laid-out window, resizing the hidden window to strip geometry.
- `SectionsPanelSizeChanged:348` would compute the horizontal font scale for a vertical layout.

Blast radius is small: the subsequent save is **not** corrupted, because `SaveCurrentPlacement:296` requires `height >= MinimumHeight` (120) and a 40px strip fails that test; and `ShowWidget:146-152` repairs the geometry. So this is a transient wrong size on a window nobody can see.

**Fix.** Have `ClampMinimumSize`, `SectionsPanelSizeChanged` and `ComputeShowPeak` read `_appliedOrientation` too. `_appliedOrientation` is by definition "what is currently on screen", which is exactly what all three are reasoning about. Closes the split entirely at no cost.

**Status:** `open`

## C1-6 `[CLEANUP]` — `DerivedStripWidth` and `SectionsPanelSizeChanged` derive the font scale from two different heights

`NetworkMonitor/MiniGraphWindow.xaml.cs:769, 348`

`DerivedStripWidth` uses `AppWindow.Size.Height / scale` (the **window** height, including the ~7px resize frame and the 4+4 panel padding); `SectionsPanelSizeChanged` uses `args.NewSize.Height` (the **panel** height). At the 40px default both clamp to 1.0 and agree, so the defect is invisible at the shipped default — but they diverge at any taller strip.

**This is the same root cause as C2-3**, which quantifies the consequence (~17% excess width) and owns the fix. Recorded here because the lifetime chunk found it independently; fix once, under C2-3.

**Status:** `open` — see C2-3

## C1-7 `[CLEANUP]` — `SetWinEventHook`'s return value is not checked

`NetworkMonitor.Services/Platform/TaskbarTopmostGuard.cs:34`

If the hook fails to install, `_hook` is `IntPtr.Zero`, the guard silently does nothing forever, and there is no log line to say the taskbar-topmost behaviour is off. That is precisely the "strip buried under the taskbar" symptom the class exists to prevent, so a silent failure is indistinguishable from the bug it fixes.

**Fix.** One `AppLog` call when the returned handle is zero.

**Status:** `fixed` — 2026-08-11, fix-phase batch 3. `TaskbarTopmostGuard`'s constructor logs when `SetWinEventHook` returns `IntPtr.Zero`, saying the widget will not be restored above the taskbar.

## C1-9 `[CLEANUP]` — `Loaded`/`Unloaded` subscription pairs have no `-=` insurance

`NetworkMonitor/Views/TrafficHostPage.xaml.cs:88,93` · `NetworkMonitor/Views/SettingsPage.xaml.cs:165,170`

Balanced in the normal navigation flow, and both handlers are idempotent, so a double-`Loaded` (WinUI can raise it without an intervening `Unloaded` on a re-parent) would only double-invoke a harmless assignment. Cheap insurance to add a `-=` before each `+=`.

**Status:** `open`

## C1-10 `[CLEANUP]` — `MiniGraphViewModel` subscribes `_state.Changed` in its constructor and never unsubscribes

`NetworkMonitor/ViewModels/MiniGraphViewModel.cs:25`

Not a leak — both `MiniGraphViewModel` and `MiniGraphState` are DI singletons with identical lifetimes. Noted because it is the one subscription in the whole feature with no matching removal, while `SettingsPage` and `TrafficHostPage` both pair theirs with an `Unloaded` teardown; and because it means `Refresh()` runs on every state change even when the widget has been closed for hours. Trivial cost.

**Status:** `open`
