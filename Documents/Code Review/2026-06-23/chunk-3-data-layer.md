## Findings

### C3-1 [RISK/maintainability] `EnsureCreated` and hand-written `CREATE TABLE` DDL can diverge
`AppDbContext.cs`. Schema is created two ways: EF `EnsureCreatedAsync` (from the `DbSet` model: Device, ScanSession, DeviceEvent, TrafficEntry, DigestReport) **and** hand-written `CREATE TABLE IF NOT EXISTS` guards (DeviceEvents, TrafficEntries, TrafficRollups, DigestReports). Two issues:
- The hand DDL for DeviceEvents/TrafficEntries/DigestReports duplicates what EnsureCreated already generates; if the model and the literal DDL ever drift (column type/name/nullability), a fresh DB and an upgraded DB end up with different schemas.
- `TrafficRollups` is **not** an EF entity (no `DbSet`), so it exists *only* via the manual guard — EnsureCreated never creates it.
**Why it's structured this way:** `EnsureCreated` only acts when the DB file doesn't exist; on an existing DB it's a no-op. The manual `IF NOT EXISTS` guards are the no-migrations way to add new tables to already-deployed DBs. Functional, but the duplication is a latent drift hazard.
Status: **FIXED 2026-06-25 (C3-2)** — all manual DDL removed; `EnsureCreated` is now the sole schema source, so the drift hazard is gone.

Per your stance (any DB change ⇒ a new DB), they're dead weight: a fresh DB is created with the correct schema by `EnsureCreated`, and traffic data is regenerated by capture anyway.
**Recommendation:**

Cleanest end-state: make TrafficRollups an entity, delete all manual DDL + migrations, rely solely on `EnsureCreated`, and wipe the DB on schema bumps.

### C3-4 [RISK] `Settings.Save()` / `SortPreference.Save()` are non-atomic and unguarded
`Settings.cs:18-25`, `SortPreference.cs:36-39` — both do a bare `File.WriteAllText` with no try/catch and no temp-file+rename. A crash or power loss mid-write corrupts `settings.json` / `sort-*.json`; an IO error (file locked, AV scan) throws straight out of the call — and these are invoked from **UI property setters** (e.g. the documented `SetProperty` pattern calls `_settings.Save()`) and grid sort handlers, so the exception would surface in the UI.
**Fix:** write to a temp file then `File.Move(..., overwrite: true)`, and wrap in try/catch (Settings) / the existing pattern (SortPreference.Save has none; Load does).
Status: **FIXED 2026-06-25 (data-integrity batch)** — new `Data/AtomicFile.WriteAllText` writes to `<path>.tmp` then `File.Move(temp, path, overwrite:true)`, wrapped in try/catch (creates the dir too). `Settings.Save()` and `SortPreference.Save()` both route through it → atomic + non-throwing.

### C3-5 [RISK — verify in Chunk 4] OUI vendor lookup may fail on dash-formatted MACs
`OuiDatabase.cs`. `Load` normalizes prefixes to colon-lowercase (`Replace("-", ":").ToLowerInvariant()`, keys like `aa:bb:cc`). But `Lookup` does `macAddress[..8].ToLowerInvariant()` with **no** dash→colon conversion. Windows `arp -a` emits MACs with **dashes** (`aa-bb-cc-dd-ee-ff`). If `Device.MacAddress` is stored in dash form, `Lookup` produces `aa-bb-cc`, which never matches the `aa:bb:cc` keys → vendor always null.
**Action:** verify the MAC normalization in `NetworkScanner`/`DeviceTracker` (Chunk 4). If MACs are stored with dashes (or mixed), this is a real correctness bug; fix by normalizing both sides identically.
Status: open (cross-ref Chunk 4)
