# Speed Test feature — design

Date: 2026-06-28

## Goal

Periodically measure internet speed (download, upload, latency, jitter) against a free,
keyless service, store the results, and surface them on the Traffic page with on-demand
testing and CSV export.

## Decisions (settled)

- **Service**: Cloudflare's free `speed.cloudflare.com` endpoints (no API key, no EULA,
  plain `HttpClient`). Google's search speed test is M-Lab/NDT under the hood and offers no
  callable API; Cloudflare gives the same class of result with far less code.
- **Metrics**: download (Mbps), upload (Mbps), latency (ms), jitter (ms).
- **Schedule**: fixed **1-hour** interval. No interval setting. The manual button covers
  running it more often.
- **Enable/disable**: a single `SpeedTestEnabled` toggle in Settings.
- **Retention**: no dedicated setting — reuse the existing `Settings.TrafficPurgeDays`
  (default 7) to purge speed-test rows, folded into the existing traffic purge.
- **Presentation**: the "Traffic" nav item becomes a host page with two tabs — **Traffic**
  (the existing page) and **Speed Test** (new) — following the `DevicesHostPage` pattern.
- **Trend chart**: the Speed Test tab has a chart at the top in a card styled identically to
  the live traffic chart (same blue download / purple upload area+line styling and hover
  tooltip), implemented as a new lightweight `SpeedTrendChart` control that plots Mbps over
  the retained period. It deliberately does **not** reuse `TrafficAreaChart` (which is built
  for dense, live, bytes/sec data and would mislabel a sparse hourly Mbps series).
- **CSV export**: yes, matching the device/history pages.
- **Completion notification**: every completed test (manual + hourly) shows an in-app banner
  always, plus an OS toast gated on the existing `ShowToasts` setting.
- **No** slow-speed (threshold) alerts in v1.

## Components

### 1. Measurement — `Services/SpeedTest/SpeedTestService.cs`

Runs one full test against Cloudflare using a shared `HttpClient`:

- **Latency + jitter**: several quick `GET /__down?bytes=0` requests; latency = mean RTT,
  jitter = mean absolute difference between consecutive RTTs (Cloudflare's own method).
- **Download**: `GET /__down?bytes=25000000`, timing the byte stream → Mbps.
- **Upload**: `POST /__up` with a generated byte body, timing it → Mbps.
- Captures the Cloudflare colo/server identifier (response header) for display.
- Returns a `SpeedTestResult`. On failure, returns a result with `Success = false` and the
  error message — no exception escapes the service.

### 2. Data model — `Models/SpeedTestResult.cs`

New entity and `DbSet<SpeedTestResult>` on `AppDbContext`:

| Field | Type | Notes |
|---|---|---|
| `Id` | `int` | PK |
| `Timestamp` | `DateTime` | UTC |
| `DownloadMbps` | `double` | |
| `UploadMbps` | `double` | |
| `LatencyMs` | `double` | |
| `JitterMs` | `double` | |
| `Server` | `string` | Cloudflare colo |
| `Success` | `bool` | |
| `Error` | `string?` | populated when `Success` is false |

Indexed on `Timestamp`. The app uses `EnsureCreated` (no migrations), so **the local DB
must be deleted once** for the new table to be created.

### 3. Background worker — `Services/SpeedTest/SpeedTestWorker.cs`

A `BackgroundService` mirroring `ScanWorker`:

- Run loop: `await Task.Delay(TimeSpan.FromHours(1))` first, then if `SpeedTestEnabled`, run a
  test → save to DB → raise `SpeedTestCompleted`. Interval is a hard-coded constant. The delay
  precedes the first run (so the first automatic test is ~1 hour after launch), matching
  `ScanWorker`'s "starts after the first interval" behaviour; the **Run Speed Test** button
  covers an immediate run.
- A `SemaphoreSlim` gates scheduled vs. manual runs so they never overlap.
- Exposes `RunNowAsync()` for the manual button.
- Registered in `App.xaml.cs` DI as a singleton + hosted service (same as `ScanWorker`).
- Raises `SpeedTestCompleted` so the ViewModel can refresh and `MainWindow` can notify.

The worker does **not** own a purge loop — purge is folded into the existing traffic purge
(see below).

> Note: a running speed test moves real data and will briefly spike the live traffic chart.
> This is expected, not a bug.

### 4. Purge — fold into `ScanWorker.PurgeOldHistoryAsync`

Inside the existing `if (settings.TrafficPurgeDays > 0)` branch, add a delete of
`SpeedTestResult` rows with `Timestamp < trafficCutoff`. One setting purges traffic and
speed-test data together. No second purge loop.

### 5. Settings — `Data/Settings.cs`

Add a single property:

```csharp
public bool SpeedTestEnabled { get; set; } = true;
```

Surfaced on `SettingsPage` as a toggle using the existing instant-save-on-change pattern.
No interval or retention setting (interval is fixed; retention reuses `TrafficPurgeDays`).

### 6. UI — Traffic host page + Speed Test tab

**`Views/TrafficHostPage.xaml`** (new) mirrors `DevicesHostPage`: a `SelectorBar` with two
items — **Traffic** and **Speed Test** — over two `Frame`s. The first frame hosts the
existing `TrafficPage` (unchanged); the second hosts the new `SpeedTestPage`. The "Traffic"
nav item in `MainWindow` (tag `traffic`) navigates to `TrafficHostPage` instead of
`TrafficPage`, and the nav handler in the code-behind is updated accordingly.

**`Views/SpeedTestPage.xaml`** (new) contains, top to bottom:

- A **trend chart** (`Views/Controls/SpeedTrendChart`, new) in a card styled identically to
  the traffic chart — same blue download / purple upload area+line styling and hover tooltip
  — plotting **download and upload Mbps** over the retained period. Static (no live scroll),
  Mbps-formatted axis/hover.
- A **latest-result tile**: download / upload / latency / jitter, with timestamp + server.
- A **Run Speed Test** button styled like the Devices page "Scan Network" button:
  `AccentButtonStyle`, bound to a `RunNowCommand`, with an adjacent `ProgressRing` bound to
  an `IsRunning` property that is active while a test runs.
- A **history `DataGrid`** (timestamp, download, upload, latency, jitter), styled like the
  existing grids.
- An **Export CSV** button.

A new DI-registered `ViewModels/SpeedTestViewModel.cs` backs the page, kept isolated from
`TrafficViewModel`. It loads history, exposes the latest result and the chart points, an `IsRunning` flag, the
`RunNowCommand` (delegating to `SpeedTestWorker.RunNowAsync`), and subscribes to
`SpeedTestCompleted` to refresh.

### 7. Completion notification — `MainWindow`

On **every** completed test (manual and hourly background), notify the user, mirroring the
daily-digest completion pattern:

- **In-app banner** — always shown via `InAppNotificationService.Show(message)`
  (→ `MainWindow.OnNotificationRequested`).
- **OS toast** — classic `ToastNotificationManager` (not App SDK), shown **only when
  `Settings.ShowToasts` is true**, consistent with device toasts.

`MainWindow` injects `SpeedTestWorker` and subscribes to its `SpeedTestCompleted` event,
then shows the banner and (conditionally) the toast on the dispatcher thread. The worker
itself stays UI-free and only raises the event.

Message format on success: `Speed test: 245.0 ↓ / 18.0 ↑ Mbps · 12 ms`. On failure:
`Speed test failed: <error>`.

### 8. CSV export — `Services/Csv/SpeedTestCsvExporter.cs`

Reuses `CsvField` and `Win32FileSaveDialog`. Output file name follows the existing
convention: `Umnatha Network Monitor SpeedTests yyyy-MM-dd.csv`. Columns: timestamp,
download (Mbps), upload (Mbps), latency (ms), jitter (ms), server, success.

## DI registration (`App.xaml.cs`)

- `SpeedTestService` (singleton or transient).
- `SpeedTestWorker` as a singleton, also registered as the hosted service, and exposed for
  the ViewModel's manual trigger (same dual registration as `ScanWorker`).
- `SpeedTestViewModel`.

## Out of scope (v1)

- Slow-speed threshold alerts / toasts.
- Configurable interval or dedicated retention setting.
- Latency/jitter on the trend chart (they remain in the history grid only; the chart plots
  download and upload Mbps, matching the two-series traffic chart).

## DB impact

A new table is added. Because the app uses `EnsureCreated` (no EF migrations), the local
database file must be deleted once so the schema is recreated with the `SpeedTestResults`
table.
